# Replication Package

Replication package of the paper *Automatic Test Data Generation for RESTful
APIs: A Case Study on a Governmental System*. The study compares four
techniques implemented in [EvoMaster](https://www.evomaster.org), MIO, RANDOM,
WTS, and SMARTS, in black-box mode on the CMDE API.

The package has two parts:

- **Revised evaluation (2026).** The results reported in the paper: a main
  campaign (30 blocks, 120 executions) and a low-budget campaign (10 blocks,
  40 executions), both with EvoMaster 6.2.0 against a local deployment of the
  API with fictitious records.
- **Initial study (2025).** The original executions with EvoMaster 3.4.0
  (RANDOM, WTS, and SMARTS), kept as they were. The paper reports them
  recomputed with the corrected coverage tool.

## Raw data of the 2026 campaigns

The raw data of the two 2026 campaigns (about 2.7 GB) are not in Git because of
their size. They are published on Zenodo,
<https://doi.org/10.5281/zenodo.24148473>, as two archives:

| Archive | Size | Campaign | Executions | Files |
|---|---|---|---|---|
| `official-6.2.0.tar.gz` | 2.0 GB | main campaign | 30 blocks × 4 techniques | 5,053 |
| `low-budget-6.2.0.tar.gz` | 83 MB | low-budget campaign (`ratePerMinute 20`) | 10 blocks × 4 techniques | 1,688 |

`SHA256SUMS` holds the checksum of each archive, and `MANIFEST-*.txt` the
checksum of every file inside it. Extract the archives into
`tool/data_generated/`, or anywhere else and set `CMDE_DATA` to that directory;
the scripts in `analysis/jss-revision/` read the data from there.

Each campaign directory holds the plan (`plan.json`, block order and seeds),
the runner's log, and one directory per execution,
`repetition_<block>/<technique>/`, with:

- `run.json`: the execution's technique, seed, and the start, end, and duration
  of each phase;
- `generated_tests/`: the suite generated by EvoMaster and its reports;
- `statistics.csv` and `covered_targets.txt`: EvoMaster's own statistics;
- `extracted_test_data.json` and `criteria_analyzed/`: the requests of the
  generated tests and the coverage of each criterion;
- `suite_http.jsonl.gz` and `suite_without_assertions_http.jsonl.gz`: every
  HTTP exchange of the two re-executions of the suite (with assertions and
  without them);
- `search_logs/`, `suite_logs/`, `suite_without_assertions_logs/`: the API's
  logs (nginx, Laravel, queue worker) of the search and of each re-execution.

## Sensitive data

The API targeted by this study (CMDE, *Conjunto Mínimo de Dados
Educacionais*, maintained by Brazil's Ministry of Education) receives the data
that feeds the Pé-de-Meia program. Its **documentation is public**
(<https://api-cmde.gestaopresente.mec.gov.br/docs?api-docs.json>), so the
OpenAPI specifications and the criteria derived from them are included without
restriction.

- **API keys.** The campaigns used API keys of the development environment,
  which are not public. They were replaced with `REDACTED_API_KEY` everywhere
  they appeared: in the 76 affected files of the initial study, and in the
  published archives of the 2026 campaigns (generated tests, EvoMaster
  statistics and reports, extracted test data, and Laravel logs). The HTTP
  captures of 2026 never recorded the key. To re-execute a generated suite,
  replace the placeholder with a valid key.
- **2026 records.** The local deployment held only fictitious records of
  people, generated by `tool/generate_synthetic_data.py` (see the protocol);
  the remaining tables hold domain data (codes, schools, institutions) with no
  personal data.
- **2025 payloads.** The payloads of the 2025 tests (names, CPFs, addresses)
  are synthetic data generated by EvoMaster for fuzzing: no evidence of real
  student data was found in the samples checked (names such as "Donald
  Jackson", addresses such as "Rua teste", repeated digit strings such as
  "11111111111"). The files were not audited one by one; if you reuse this
  material, that check is worth doing.

The `evomaster.jar` binary is not versioned here; download it from the
[official EvoMaster releases](https://github.com/WebFuzzing/EvoMaster/releases)
(the protocol gives the SHA-256 of the 6.2.0 jar used in 2026).

## Corrections to the coverage tool

The revised paper measures coverage with a corrected version of the tool in
`tool/`, which also recomputes the initial study
(`analysis/jss-revision/recompute_2025.py`). The corrections (commit
`c58c91d`) are:

- Request Parameter Coverage (RPC) now includes the declared header parameters
  and the request-body fields, and Request Parameter Value Coverage (RPVC) the
  enum and boolean values of those inputs. For the initial study this adds 158
  body fields (RPC: 43 to 201 elements) and 120 body values (RPVC: 12 to 132).
- Status Code Class Coverage (SCCC) expects one success class (2XX) and one
  error class (any 4XX or 5XX response) per operation; the earlier version
  counted only 4XX as the error class.
- Boolean and numeric enum values were compared as Python values against the
  strings sent in the request and could never be covered; they are now
  compared as text. A path parameter value was compared character by
  character; it is now compared as a whole.
- Calls whose URL was built with `resolve_location(...)` were lost (130 SMARTS
  calls in the initial study), query parameters sent with an empty value were
  dropped, and a `parameters` list declared on a path item stopped the
  extraction; all three are now handled.
- Reading a nested response property now also covers the enclosing properties
  whose presence it proves.

With the corrected tool, Path, Operation, and Status Code Coverage, and the
required elements of Response Body Properties Coverage, still reproduce the
published results of the initial study in all 30 of its runs. The tool's test
suite is in `tool/tests/`.

## Reproducing the 2026 campaigns

The campaigns ran with `tool/campaign.py`, Java 17 (Eclipse Temurin 17.0.21+9),
and EvoMaster 6.2.0:

```bash
cd tool
python campaign.py --config configs/campaign-6.2.0.json --output data_generated/official-6.2.0
python campaign.py --config configs/campaign-6.2.0-low-budget.json --output data_generated/low-budget-6.2.0
```

Before every execution, the runner restores a local deployment of the CMDE API
(database, queues, and containers), as described in
`docs/reexecution-protocol.md`. The API's code is not public, so re-running
against CMDE requires access to it and a valid key; against another API, the
`environment` section of the campaign file and the reset step must be adapted.

## Initial study (2025)

### Which data is the official run

The `results/statistics/` folder contains aggregated summaries from **4
complete runs** (10 repetitions × 3 techniques each), performed on different
dates. **Only one of them is the dataset of the initial study**, and it is the
only one whose complete raw data is in `results/official-run/`:

| Run | Configured `max_time` | Official dataset? | Raw data included? |
|---|---|---|---|
| `experiment-date-03-05-25-time-01-29-53-388` | 15m | No (pilot) | No (summary only) |
| **`experiment-date-03-05-25-time-21-29-51-725`** | **30m** | **Yes** | **Yes, `results/official-run/`** |
| `experiment-date-05-05-25-time-00-15-46-626` | 20m | No (pilot) | No (summary only) |
| `experiment-date-06-05-25-time-19-56-26-372` | 15m | No (pilot) | No (summary only) |

`results/official-run/` holds the specification archived at the time of the
experiment (`api-docs.json`, identical to `specification/archived/`), the
criteria extracted from it (`criteria/`), and, for each of the 10 repetitions
and 3 techniques, the generated tests (key redacted), EvoMaster's raw log
(`execution_output.txt`), the coverage per criterion (`criteria_analyzed/`),
the covered targets, and the extracted test data.

### Reproducing the analysis of the initial study

`analysis/compute_statistics.py` and `analysis/generate_figures.py` reproduce
the numbers and figures of the paper **as first submitted**, from
`results/statistics/*.csv` and `results/official-run/`:

```bash
cd analysis
pip install -r requirements.txt
python compute_statistics.py    # prints every number of the first submission
python generate_figures.py      # writes the figures to analysis/output/
```

The revised paper reports the initial study recomputed with the corrected
coverage tool; `analysis/jss-revision/recompute_2025.py` does that
recomputation. If the minimization-phase data
(`results/statistics/minimization_analysis.csv`) needs to be regenerated from
the raw logs, run `python tool/analyze_minimization.py` first.

### Reproducing the 2025 experiment

1. Copy `tool/configs/em.yaml.example` to `tool/configs/em.yaml` and set
   `bbSwaggerUrl` to the target API's OpenAPI specification, along with
   `maxTime` and any other options
   ([EvoMaster options](https://github.com/WebFuzzing/EvoMaster/blob/master/docs/options.md)).
2. Adjust `tool/configs/setup_experiment.json` with the algorithms and the
   number of repetitions.
3. Download `evomaster.jar` (3.4.0 for the initial study) and place it in
   `tool/`.
4. Run with Docker (`docker compose up --build`) or locally
   (`python tool/main.py`, Python 3.8+ and Java 8).

Results are saved under `tool/data_generated/<experiment_name>/`, and the
statistics CSV can be generated with
`python tool/run_get_statistics_csv.py -n <experiment_name>`.
