# Replication Package

This directory contains the tool and aggregated results used in the study on
automatic test data generation for RESTful APIs (RANDOM, WTS, and SMARTS
techniques, via [EvoMaster](https://www.evomaster.org)).

## ⚠️ About sensitive data

The API targeted by this study (CMDE — Conjunto Mínimo de Dados Educacionais,
maintained by Brazil's Ministry of Education) receives the data that feeds the
Pé-de-Meia program, one of the federal government's major public policies.
The **API documentation is public**
(<https://api-cmde.gestaopresente.mec.gov.br/v1/documentation>), so the
OpenAPI specification (`api-docs.json`) and the criteria derived from it
(`criteria/*.json`) are included in this package without restriction.

> **Version note:** the `api-docs.json` included here is a copy **archived at
> the time of the experiment** (May 2025). The public documentation at the
> link above may have changed since then — do not assume the two are
> identical.

The tests generated by EvoMaster (`generated_tests/*.py`, under
`results/official-run/`), on the other hand, had **a real authentication key
(`x-api-key`) used to access the API** embedded in every request. Unlike the
specification, this key is not public information — it was **redacted
(replaced with `REDACTED_API_KEY`) in all 76 affected files** before being
included here. The payload content (names, CPFs, addresses, etc.) that
appears in these tests is **synthetic data automatically generated by
EvoMaster** for fuzzing purposes — no evidence of real student data was found
in the samples checked (names such as "Donald Jackson"/"Timothy Garcia",
addresses such as "Rua teste", emails such as "elegibel@elegivel.com", and
repeated digit strings such as "11111111111" are typical patterns of
fuzzer-generated data, not real records). That said, the files were not
audited one by one — if you plan to reuse this material, that check is worth
doing.

The `evomaster.jar` binary is not versioned here; download the version used
directly from the
[official EvoMaster repository](https://github.com/WebFuzzing/EvoMaster/releases).

## Results: which file is the "official" one

The `results/statistics/` folder contains aggregated summaries from **4
complete runs** (10 repetitions × 3 techniques each), performed on different
dates during the study's development. **Only one of them is the dataset
reported in the paper** — and it is the only one whose complete raw data is
in `results/official-run/`:

| Run | Configured `max_time` | Used in the paper? | Raw data included? |
|---|---|---|---|
| `experiment-date-03-05-25-time-01-29-53-388` | 15m | No (pilot) | No (summary only) |
| **`experiment-date-03-05-25-time-21-29-51-725`** | **30m** | **Yes — official dataset** | **Yes — `results/official-run/`** |
| `experiment-date-05-05-25-time-00-15-46-626` | 20m | No (pilot) | No (summary only) |
| `experiment-date-06-05-25-time-19-56-26-372` | 15m | No (pilot) | No (summary only) |

> **Note:** the actual `max_time` used in the official run (the 21:29:51 one)
> was 30 minutes per execution, consistent with the 30-minute search budget
> described in the paper.

### What's in `results/official-run/` that hasn't been used in the paper yet

Beyond what is already reported in the paper's tables, every
`execution_output.txt` records two metrics that were never explored: **real
execution time** (`Passed time (seconds)`) and a count of **fault
indicators** (`Potential faults`) automatically detected by EvoMaster. The
`generated_tests/EvoMaster_faults_Test.py` files contain concrete examples of
these indicators (endpoint, payload, response). The specification findings
discussed in Section 5.4 of the paper (undeclared status codes, schema
inconsistencies, pagination typing, etc.) were extracted from exactly these
files; the two metrics themselves (real execution time and fault potential)
remain an unexplored direction for future work.

## How to reproduce the statistical analysis and figures

Every statistical number (Shapiro-Wilk, Kruskal-Wallis, Dunn's post-hoc test
with Bonferroni correction, Spearman correlation, η²_H effect sizes) and every
result figure in the paper is recomputed directly from the data already
included in this package (`results/statistics/*.csv` and
`results/official-run/*/execution_output.txt`) — there is no need to rerun
the experiment for this.

```bash
cd analysis
pip install -r requirements.txt
python compute_statistics.py    # prints every number reported in the paper
python generate_figures.py      # writes the 6 figures to analysis/output/
```

`compute_statistics.py` was checked number by number against the paper's text
and tables (Sections 5.1–5.3) before being included here. `generate_figures.py`
reproduces the same figures used in the paper (`../../figuras/` in the main
repository) from the raw data.

If the minimization-phase data (`results/statistics/minimization_analysis.csv`)
needs to be regenerated from the raw logs, run this first:

```bash
python tool/analyze_minimization.py
```

## How to reproduce the experiment

To run the experiment again against CMDE (requires your own `x-api-key`, not
included here) or against another REST API with an OpenAPI specification:

1. Copy `tool/configs/em.yaml.example` to `tool/configs/em.yaml` and set
   `bbSwaggerUrl` to the target API's OpenAPI specification (for CMDE:
   <https://api-cmde.gestaopresente.mec.gov.br/v1/documentation>), along with
   `maxTime` and any other desired options
   ([EvoMaster options documentation](https://github.com/WebFuzzing/EvoMaster/blob/master/docs/options.md)).
2. Adjust `tool/configs/setup_experiment.json` with the desired algorithms and
   number of repetitions.
3. Download `evomaster.jar` (see link above) and place it in `tool/`.
4. Run with Docker (`docker compose up --build`) or locally
   (`python tool/main.py`, requires Python 3.8+ and Java 8).

Results are saved under `tool/data_generated/<experiment_name>/`, and the
statistics CSV can be generated with:

```bash
python tool/run_get_statistics_csv.py -n <experiment_name>
```
